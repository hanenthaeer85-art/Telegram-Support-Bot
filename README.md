# بوت وسيط رسائل تيليجرام

بوت Python يرسل رسائل المستخدمين الخاصة إلى حساب المشرف، ويعيد رد المشرف إلى المستخدم الصحيح عند استخدام Reply على الرسالة التي وصلت من البوت.

## الوظائف

- يرسل `/start` رسالة الترحيب: «أهلاً بك، أرسل رسالتك وسيتم إيصالها إلى الإدارة.»
- ينسخ الرسائل النصية والصور والأنواع الأخرى التي يدعم Telegram `copyMessage` نسخها إلى المشرف، مع بطاقة تعريف منفصلة.
- يمكن للمشرف الرد على بطاقة التعريف أو على نسخة الرسالة نفسها.
- تُحفظ علاقة رسائل المشرف بالمستخدمين ومعرّفات التحديث في SQLite، لتبقى بعد إعادة تشغيل العامل.
- يعيد المحاولة عند انقطاع الاتصال، ويسجل الأخطاء دون طباعة رمز البوت.

## الإعداد

أضف متغيري البيئة التاليين إلى إعدادات الاستضافة:

- `BOT_TOKEN`: رمز البوت من BotFather، واحفظه كسر.
- `ADMIN_ID`: معرّف Telegram الرقمي لحساب المشرف.

افتح البوت بحساب المشرف وأرسل `/start` مرة واحدة، ثم شغّل العامل. على المستخدمين إرسال `/start` إلى البوت قبل مراسلته.

للتشغيل المحلي:

```sh
python -m bot.main
```

## النشر على Render

هذا عامل طويل التشغيل يستخدم Telegram long polling، لذلك يجب أن يكون **Background Worker** وليس Web Service أو Cron Job؛ لا يحتاج إلى منفذ HTTP أو نطاق عام. ينشئ ملف `render.yaml` العامل والقرص الدائم وإعداداتهما، وأمر البدء فيه يطابق الأمر في `Procfile`.

1. من لوحة Render اختر **New + → Blueprint**، ثم اربط مستودع المشروع والفرع الذي يحتوي على `render.yaml`.
2. اختر **المنطقة** المناسبة يدويًا، ثم اختر **خطة تشغيل مدفوعة** للعامل. القرص الدائم يتطلب خدمة مدفوعة؛ لا تترك الخدمة على خطة غير مدعومة.
3. أدخل `BOT_TOKEN` في لوحة Render عند طلبه، واحفظه كسر هناك فقط. أدخل أيضًا `ADMIN_ID`، وهو معرّف Telegram الرقمي للمشرف. لا تضع أيًا منهما في `render.yaml` أو الشفرة أو ملفات المشروع أو أوامر الطرفية أو السجلات.
4. راجع الإعدادات التي ينشئها Blueprint: عامل Python واحد، وقرص دائم بحجم 1GB مركّب على `/var/data`، و`BOT_DB_PATH` مضبوط إلى `/var/data/telegram-relay.sqlite3`. يمكن زيادة حجم القرص لاحقًا إذا احتجت إلى مساحة أكبر. لا ترفع عدد النسخ ولا تنشئ عاملًا ثانيًا يستخدم رمز البوت نفسه، حتى لا تتنافس عمليتا polling على التحديثات.
5. أكمل إعداد Blueprint وانشر الخدمة. في السجلات، تحقق من ظهور رسالة بدء العامل ومسار قاعدة البيانات، دون طباعة متغيرات البيئة. لإعادة تشغيله يدويًا استخدم **Deploys → Manual Deploy → Restart service**؛ يستقبل العامل `SIGTERM` ويتوقف وينظف اتصال SQLite، بينما يبقى الملف داخل القرص الدائم بعد إعادة التشغيل والنشر.

يكتب SQLite ملفات قاعدة البيانات وملفات WAL المرافقة لها تحت `/var/data`، لذلك تبقى بيانات ربط الرسائل محفوظة ما دام هذا المسار على القرص. أي ملفات خارج مسار القرص تظل مؤقتة في Render.

مراجع Render: [Background Workers](https://render.com/docs/background-workers)، [Persistent Disks](https://render.com/docs/disks)، [Environment Variables and Secrets](https://render.com/docs/configure-environment-variables)، [Scaling](https://render.com/docs/scaling).

للاستضافة محليًا، المسار الافتراضي هو `data/telegram-relay.sqlite3`، ويمكن ضبطه عبر `BOT_DB_PATH`. لا تعتمد على هذا المسار الافتراضي في خدمة سحابية تحذف ملفاتها عند إعادة النشر.

## ملاحظات التشغيل

- لا تضع `BOT_TOKEN` في الشفرة أو في مستودع Git.
- عند تغيير رمز البوت، حدّث السر في إعدادات الاستضافة وأعد تشغيل العامل.
- إذا تعذر على البوت مراسلة المشرف، تأكد أن حساب المشرف بدأ محادثة مع البوت وأن `ADMIN_ID` صحيح.
- إذا أرسل المشرف رسالة جديدة بدل Reply، فلن يستطيع البوت معرفة المستخدم المقصود؛ يجب الرد باستخدام Reply.
